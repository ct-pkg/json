# ADR-0004：数字采用双轨表示

- 状态：已采纳（Accepted）
- 日期：2026-11-15
- 裁定者：用户
- 回答：ADR-0002 待定 3（写入数字的精度策略）
- 前提：[ADR-0001](0001-tree-data-model.md) 设计口径 3、[ADR-0002](0002-mutable-scope.md) 读 + 写范围
- 影响面：数字节点的存储与编码。本 ADR 不含实现，不改变当前 `json.ct`。

## 决策

数字分两条来源，各走各的表示：

1. **从文本解析来的数值节点保留原始字面量**，编码时原样回吐：`1.0` 还是 `1.0`，超长整数不丢位。
2. **程序写入的值按类型分两支**：整数用 64 位精确存，浮点用 `double`。
3. 因此节点需要一个「字面量来源」标记和一个数值分支，两套逻辑并存。

## 已知代价

两套数字逻辑并存是**已知代价**，不要试图统一成一种：统一成字面量会让写入端被字符串/词法形式绑架；统一成 `double` 会让解析端丢精度，与 ADR-0001 的口径冲突。节点多一个来源标记与一个分支，读路径与编码路径都要按来源分派。

## 后果

- **解析侧往返无损**：`1.0`、`1e3`、超出 `int64`/`double` 精度的长整数都按原词回吐；这条只说编码，不改变读 API 的取值口径。
- **写入侧**：整数在 64 位内精确；浮点受 `double` 精度限制，超过 2^53 的整数如果按浮点写入会丢位，调用方要按整数支写入。
- **编码必须按来源分支**：解析来的节点用原字面量；程序写入的整数用十进制；程序写入的浮点见下条未定。
- **节点体积增加**：来源标记 + 数值分支，具体布局不在本 ADR 决定。

## 未定（本次裁定未覆盖）

程序写入的浮点如何编码，本次没有裁定：

- `double` 的输出格式（`%.17g` 之类定长，还是最短往返表示）；
- 整值浮点的输出（写入 `1.0` 是吐 `1` 还是 `1.0`）；
- 非有限值（`NaN` / `Inf`）的处置（现有实现报 `JSON_EMIT_FINITE`，新模型是否沿用未定）。

这些不在本 ADR 的裁定范围内，实现前需要另行拍板；本 ADR 不替用户选择。

## 不做什么

- 不写实现、不恢复开发、不新建夹具、不修改 `json.ct`。
- 不定义节点结构体、函数签名与错误码。
