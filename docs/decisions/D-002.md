## 争点

UTF-8 校验、BOM 与含 NUL 键/值的默认承诺。

## 判据（逐条）

| # | 判据 | 来源 |
| --- | --- | --- |
| 1 | 合法输入的定义唯一，默认行为可判定 | R-A-08、R-A-12 |
| 2 | 同一合法文档在两种模式下根视图一致 | R-A-08 |
| 3 | 含 `\u0000` 的值与键可往返 | R-B-04、R-D-06 |

## 判决（upheld）

1. 默认宽松：不校验输入 UTF-8，≥0x80 字节原样透传；这与现状一致。
2. PH-4 新增 strict 入口 `json_decode_strict(char *text, int len, JsonRef *out)`；非法 UTF-8 返回新码 `JSON_ERR_UTF8`。`json_decode` 保持宽松，两者共享 parser。
3. BOM `EF BB BF` 一律按非法字符拒绝，**不**自动剥离；strict 同样拒绝。
4. 键与值都允许内嵌 NUL（`Str` 长度承载），不另设 key 限制。
5. `json_as_str` 保持「借用指针 + 长度」，不承诺 NUL 结尾。

## 生效范围

PH-4 的 strict 入口与 BOM 用例；`docs/spec/ct-json-0.1.0.md` §五的「不校验 UTF-8」表述在 PH-4 补 strict 说明。

## 理由

默认行为保持兼容，strict 是可选加严；BOM 现行就是拒绝，自动剥离会给「同一字节在两种 API 下结果不同」留下口子。键支持 NUL 已是实现事实，收窄反而要改数据结构。

## 失效条件

若上游要求 BOM 自动剥离，或用户要求默认 strict，重开。

## 影响面

PH-4；ACC-08/12/30；`json_decode_strict` 进入公开面（PH-4 更新 R-E-02 清单）。
